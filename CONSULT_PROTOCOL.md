# Nissan Consult (Consult-I / DDL1) Protocol Reference

The goal of this document is to cover everything needed to write an open-source,
cross-platform (Linux-first) replacement for tools like ECUTalk, targeting a
**1998 Nissan Maxima (A32, VQ30DE)** with a Consult-to-USB serial dongle.

Every fact here has a **source tag** (`[S1]`, `[S2]`…, listed at the bottom).
Anything marked **⚠ UNVERIFIED** has no single authoritative source, or the
sources disagree. Check those items on the car before relying on them.

## 1. What Consult is

- **Consult** ("CONSULT", later called Consult-I or DDL1) is Nissan's proprietary
  diagnostic link. It was used on roughly 1989–2000 Nissan/Infiniti vehicles. Later
  cars moved to Consult-II over K-line/ISO 14230, and Consult-III runs over CAN. `[S5][S6]`
- It is a simple **request → echo → streamed-response** byte protocol. There are no
  checksums and no addressing beyond the init byte that selects which ECU you
  talk to (engine, A/T, HICAS, A/C). `[S1][S3]`
- The dealer tool was the Nissan CONSULT hand-held. Third-party tools such as
  ECUTalk, PLMS Consult, Nistune, DatScan, ConZult and others all speak the same
  protocol through a level-shifting interface. `[S1]`
- A 1998 Maxima is also an OBD-II car. Generic OBD-II (ISO 9141-2) on the 16-pin
  connector is a **separate** protocol and is **not** covered here. Consult gives
  far richer Nissan-specific data (A/F alpha, AAC duty, raw sensor voltages,
  active tests, ROM reads). `[S7]`

## 2. Physical / electrical layer

### 2.1 Signals

Consult is a **3-wire bus plus power**: `[S1]`

| Signal | Direction | Level / notes |
|---|---|---|
| **TX to ECU** (ECU "RX") | Interface → ECU | **12 V logic, idle low** (see 2.2) `[S1]` |
| **RX from ECU** (ECU "TX") | ECU → Interface | ECU output is **open collector**, pulled up by the interface to its logic level (5 V). **Idle high.** `[S1]` |
| **CLK** | Interface → ECU | Free-running clock **generated by the host/interface**. **153.6 kHz ±5 kHz** for 9600 baud, which is 16× the bit rate. It does **not** need to be synchronised with the data. A 5 V clock works. `[S1]` |
| +12 V, GND | | Powers the interface |
| CHK | | Not used by Consult cables `[S8]` |

Key point: **the ECU will not answer unless the clock is present.** `[S1]`
Your USB dongle already generates the clock and level-shifts TX/RX. From the PC,
it looks like an ordinary **9600 8N1 serial port**. You do not need to deal with the
clock in software.

### 2.2 Serial framing

- **9600 baud** (default). Other baud rates with a matching 16× clock "may be
  possible" but are untested. `[S1]`
- **8N1**: 1 start bit (low), 8 data bits sent **LSB first**, no parity, 1 stop bit
  (high). `[S1]`
- Raw binary bytes. No ASCII, spaces, CR/LF or checksums. `[S1]`

### 2.3 The 14-pin Consult connector ⚠ UNVERIFIED for the A32

On the 95–99 Maxima, owners report the grey **14-pin Consult connector** next to the
fuse block, by the passenger footwell / centre console. The **white 16-pin** plug is
the OBD-II port. `[S7]`

A generic 14-pin pinout circulated for 1989–2000 Nissans gives: `[S8]`

| Pin | Signal |
|---|---|
| 1 | RX (data **into** ECU) |
| 2 | TX (data **out of** ECU) |
| 6 | CHK (not used; absent on some models) |
| 7 | +12 V |
| 8 | GND |
| 9 | CLK |

The sources do not agree on pin numbers, and some forum posts quote **ECU-side** pin
numbers instead. If you build your own cable, confirm against the 1998 Maxima FSM
"EC" section wiring diagram or with a multimeter. `[S8]` You don't need to rewire
anything if you're using the existing dongle.

## 3. Using the USB dongle on Linux

The dongle is almost certainly a USB-UART chip (commonly FTDI FT232) plus the
Consult level shifter and clock oscillator. On Linux:

1. **Identify it:** plug it in, then run `lsusb` and `dmesg | tail`.
   - FTDI with the stock ID **`0403:6001`** is bound automatically by `ftdi_sio` → `/dev/ttyUSB0`. `[S9]`
   - Some Consult cables ship with a **custom FTDI PID**. A PLMS cable user got
     it working with `modprobe ftdi_sio vendor=0x0403 product=0xc7d9`. `[S10]`
     On modern kernels the equivalent is
     `echo 0403 <pid> | sudo tee /sys/bus/usb-serial/drivers/ftdi_sio/new_id`. `[S9]`
   - CH340 / PL2303 chips use `ch341` / `pl2303` instead.
2. **Permissions:** add yourself to the group that owns the port
   (`dialout` on Debian/Ubuntu, `uucp` on Arch): `sudo usermod -aG uucp $USER`.
3. **Latency (important for streaming):** by default FTDI buffers up to 16 ms
   before handing data to the host. For snappier live data, set
   `echo 1 | sudo tee /sys/bus/usb-serial/devices/ttyUSB0/latency_timer`
   (or `setserial /dev/ttyUSB0 low_latency`).
4. **termios settings** (what openconsult uses): `[S2]`
   - `open(dev, O_RDWR | O_NOCTTY | O_SYNC)`
   - `cfsetspeed(B9600)`, `CS8`, no `PARENB`, no `CSTOPB`, no `CRTSCTS`
   - `IXON/IXOFF/IXANY` off, raw mode (`c_lflag = 0`, `c_oflag = 0`)
   - In your own code, use a read timeout. openconsult uses `VMIN=1, VTIME=0`
     (blocking forever), which hangs if the ECU goes silent.
   - In Python: `serial.Serial('/dev/ttyUSB0', 9600, timeout=0.5)` (pyserial defaults
     to 8N1, no flow control). `[S3][S4]`

## 4. Byte-level session flow

### 4.1 Overview

```
Host                                  ECU
 │  FF FF EF          (init)           │
 │ ──────────────────────────────────▶ │
 │                     10              │  (ack: ready)
 │ ◀────────────────────────────────── │
 │  <cmd> [args…]                      │
 │ ──────────────────────────────────▶ │
 │              ~cmd  [args echoed]    │  (bit-inverted command, args echoed verbatim)
 │ ◀────────────────────────────────── │
 │  F0                (go / terminate) │
 │ ──────────────────────────────────▶ │
 │              FF  N  d1 … dN         │  frame
 │ ◀────────────────────────────────── │
 │              FF  N  d1 … dN         │  frame (repeats forever)
 │ ◀────────────────────────────────── │
 │  30                (stop)           │
 │ ──────────────────────────────────▶ │
 │              …end of current frame… │
 │              CF                     │  stop acknowledge
 │ ◀────────────────────────────────── │
```

### 4.2 Initialisation

- Send **`FF FF EF`** at 9600 baud, with the clock running. `[S1][S3]`
- The ECU replies **`10`**. It is then ready for commands. `[S1]`
- "In testing sometimes the initialisation string needed to be sent twice." `[S1]`
  K11Consult and Nissboard both **sleep ~2 s** after sending the init, then read
  one byte, and loop until they get `0x10`. `[S4]` openconsult discards bytes until
  it sees `0x10`. `[S2]`
- The idle timeout after init is reportedly **> 30 minutes**. Re-init may only be
  needed after the ECU loses power. `[S1]`
- The 3rd init byte selects **which ECU** answers (`EF` = engine). See [§10](#10-other-ecus-on-the-same-bus). `[S3]`

> Tip: if the ECU is already streaming (say your program crashed mid-stream),
> the init will be buried in frame data. Send `30` first, drain until `CF` or
> silence, then send the init. Nissboard does a version of this. `[S4]`

### 4.3 Command echo rule

- For every **valid** command byte, the ECU replies with the **bitwise complement**
  (`~cmd & 0xFF`). For example, `D1` → `2E`, `5A` → `A5`, `C9` → `36`. `[S1]`
- **Argument bytes** that follow a command are **echoed unchanged**. `[S1]`
  Examples: `5A 0B` → `A5 0B`; `C9 80 00` → `36 80 00`. `[S1][S2]`
- If the echo is wrong or missing, treat the command as invalid or unsupported.
  openconsult throws "Unexpected response received". `[S2]`

### 4.4 Go-ahead / terminator `F0`

After the command (or list of commands) is echoed, send **`F0`**. The ECU then
starts replying. `F0` is sent **once**; the ECU keeps streaming without further
prompts. `[S1][S2]`

### 4.5 Response frames

```
FF  N  d[0] d[1] … d[N-1]
│   │  └─ N data bytes
│   └──── byte count
└──────── frame start marker
```

- The ECU **streams frames continuously** until told to stop, even for one-shot
  queries like DTC read or ECU part number. `[S1]`
- **Data bytes can legitimately be `0xFF`**, for example RPM LSB or a temperature.
  Don't resync by searching for `FF` in the middle of a frame. Parse by length:
  read `FF`, read `N`, read exactly `N` bytes. Scan for `FF N` only to resync, and
  check that `N` equals the length you expect. K11Consult checks
  `FF 0E` for its 14-register request. `[S4]` Nissboard's byte-scanner gets this
  wrong. `[S4]`

### 4.6 Stopping

- Send **`30`**. The ECU **finishes the frame in progress**, then sends the stop
  acknowledge **`CF`** (= `~0x30`). `[S1]`
- "Data should be read until this byte is received to keep data integrity or the
  last frame dumped." `[S1]` openconsult reads and discards frames until `CF`. `[S2]`
- ⚠ Nissboard waits for **`FE`** instead of `CF`. `[S4]` The egroup spec and
  openconsult both say `CF`. Accept either, with a timeout, until verified on your ECU.
- You must stop before sending a new command.

## 5. Command reference

All values are hex.

| Cmd | Echo | Name | Args | Response data | Source |
|---|---|---|---|---|---|
| `FF FF EF` | `10` | Init (engine ECU) | — | — | `[S1][S3]` |
| `5A` | `A5` | Read register (live data) | 1 byte: register | 1 byte per requested register | `[S1][S2]` |
| `F0` | — | Go-ahead / terminate command list | — | starts frames | `[S1]` |
| `30` | `CF` | Stop streaming | — | `CF` after the current frame | `[S1]` |
| `D0` | `2F` | Read ECU part number | — | 22 (`0x16`) bytes | `[S1][S2]` |
| `D1` | `2E` | Read DTCs (self-diagnostic) | — | 2 bytes per code | `[S1][S2]` |
| `C1` | `3E` | Clear DTCs | — | (read-back of codes) | `[S1][S3]` |
| `C9` | `36` | Read ROM/RAM byte | 2 bytes: addr hi, addr lo | 1 byte per requested address | `[S1]` |
| `0A` | `F5` | Active test | 2 bytes: test register, value | — | `[S1][S3]` |
| `9F` | `60` | Stream all sensors (A/T, HICAS ECUs only) | — | all registers | `[S3]` |

(The echo values for `C1`, `0A` and `9F` follow from the complement rule. No source
shows them in a capture.)

### 5.1 `5A` – read registers (live data)

```
Single:  5A <reg> F0
Multi:   5A <r1> 5A <r2> … 5A <rn> F0      (max 20 registers per request) [S1]
Echo:    A5 <r1> A5 <r2> … A5 <rn>
Frames:  FF <n> <v1> <v2> … <vn>           (repeating)
```

- Data bytes come back **in the order requested**. `[S2][S4]`
- Multi-byte values are requested as separate registers, MSB first. For example,
  RPM is `5A 00 5A 01`, value = `(d0<<8 | d1) * 12.5`. `[S2][S3]`
- Example from K11Consult (14 registers): `[S4]`
  ```
  5A 0B 5A 01 5A 08 5A 0C 5A 0D 5A 03 5A 05 5A 09 5A 13 5A 16 5A 17 5A 1A 5A 1C 5A 21 F0
  → frames of: FF 0E <14 bytes>
  ```
- Fewer registers per frame gives a faster update rate. At 9600 baud the link
  carries at most ~960 bytes/s. A frame costs `2 + n` bytes, so the theoretical
  maximum is about 960 / (2 + n) frames per second. Real ECU rates will be lower.

### 5.2 `D0` – ECU part number

```
Send:  D0 F0       Echo: 2F     Frame: FF 16 <22 bytes>    then send 30
```

- The part-number format is `XXXX 23710-YYYYY`. `23710` is a constant that is not
  in the data. `[S1]` Example: `0488 23710-50F00`, where `50F00` is the software version. `[S1]`
- openconsult decodes it (0-indexed) as: `[S2]`
  ```c
  sprintf(pn, "%02X%02X 23710-%X%02X%02X", d[2], d[3], d[19], d[20], d[21]);
  ```
  The egroup doc says "Bytes 2 & 3" and "Bytes 19 to 22". ⚠ Its indexing base is
  ambiguous. Use the openconsult decoding and verify against the sticker on your ECU.
- The other 17 bytes are undocumented. Log them; they may hold calibration IDs.

### 5.3 `D1` – read fault codes

```
Send:  D1 F0       Echo: 2E     Frame: FF <2k> <code1> <starts1> … <codek> <startsk>
```

- Each fault is **2 bytes**: the **code number**, then the **number of engine starts
  since the fault last occurred**. A code clears itself after ~50 starts if it does
  not recur. `[S1]`
- No faults: `2E FF 02 55 00`. The doc describes this as "55 = no fault". `[S1]`
- Two faults: `2E FF 04 13 00 08 03` = codes 13 and 8. Code 8 was last seen 3 starts ago. `[S1]`
- See [§9](#9-fault-codes-dtcs) for the code table and an **encoding caveat**.

### 5.4 `C1` – clear fault codes

```
Send:  C1 F0       Echo: 3E     (frames)   then 30
```

- "Terminate command with F0 to start data stream, stop with 30." `[S1]`
- A later issue of the doc (Issue 7) notes that `C1` clears the **second** set of DTC
  registers but not the first or third, and then reads them back. `[S11]` Re-read with
  `D1` afterwards to confirm.

### 5.5 `C9` – read ROM / RAM bytes

```
Send:  C9 <hi> <lo> [C9 <hi> <lo> …] F0      (max 8 addresses per request) [S1]
Echo:  36 <hi> <lo> [36 <hi> <lo> …]
Frame: FF <n> <b1> … <bn>
```

- ROM space is `0x8000`–`0xFFFF`. RAM addresses can be read the same way. `[S1]`
- Example: `C9 80 00 C9 80 01 C9 80 02 F0` → `36 80 00 36 80 01 36 80 02 FF 03 05 03 08`
  (bytes at `0x8000..0x8002` = `05 03 08`). `[S1]`
- Reading 8 bytes at a time across the whole range dumps the ECU EPROM. Tuners use
  this to create ROM binaries. `[S1]` A ROM dumper fits easily in your tool.
- RAM reads let you watch internal ECU variables that are not exposed as registers,
  once you know their addresses from ROM disassembly.

### 5.6 `0A` – active tests

```
Send:  0A <test-reg> <value> F0
```

See [§8](#8-active-tests-0x0a). These **change engine behaviour**.

  perhaps some `25–39` OBD-II-era registers. ⚠ This is a guess. Probe each register
  individually (see §13).

## 7. Digital (bit) registers

`1 = active`. Bit positions come from the column layout of the egroup register table. `[S3]`

| Reg | Bit 7 | Bit 6 | Bit 5 | Bit 4 | Bit 3 | Bit 2 | Bit 1 | Bit 0 |
|---|---|---|---|---|---|---|---|---|
| `13` | — | — | — | A/C on switch | Power steering switch | Park/Neutral switch | Start signal (cranking) | Closed throttle position (idle sw) |
| `1E` | A/C relay | Fuel pump relay | VTC solenoid | — | — | — | Coolant fan HI | Coolant fan LO |
| `1F` | — | P/Reg control valve | Wastegate solenoid | — | IACV-FICD solenoid | — | — | EGR solenoid |
| `21` | LH bank 1=LEAN | RH bank 1=LEAN | — | — | — | — | — | — |

⚠ The source is a flattened table, and some bits are blank. Unlabelled bits may
carry other data on specific ECUs. Toggle the A/C, shift to P/N, turn the wheel and so
on while logging, to confirm each bit on the Maxima.

## 8. Active tests (0x0A)

> ⚠ **SAFETY:** These commands change fuel, timing, idle air, pumps and fans
> while the engine runs. Wrong values can cause stalls, lean misfire or detonation.
> Use them with the car stationary, in park, and with the engine warm. Always restore
> the normal value, then send `30`. Cutting the fuel pump while driving is dangerous.

Format: `0A <test-reg> <value> F0` `[S1]`

| Test reg | Test | Values | Source |
|---|---|---|---|
| `80` | Coolant temp override | `temp + 50` (`50`=30 °C, `32`=0 °C, `00`=-50 °C) | `[S1][S3]` |
| `81` | Fuel injection trim | `64` = 100 % (normal). `+1` per +1 % (`67`=+3 %, `6A`=+6 %, `6E`=+10 %, `5A`=-10 %) | `[S1][S3]` |
| `82` | Ignition timing offset | signed degrees: `00`=normal, `02`=+2°, `05`=+5°, `FE`=-2°, `FB`=-5° | `[S1][S3]` |
| `84` | IACV-AAC opening | Issue 6: signed 0.5 % steps (`00`=normal, `02`=+1 %, `FC`=-2 %). Register table: `00`=0 %, `8C`=100 %. ⚠ conflict | `[S1][S3]` |
| `85` | IACV opening | `00`=0 %, `8C`=100 % | `[S3]` |
| `87` | IACV/FICD solenoid | `00`=OFF | `[S3]` |
| `88` | Power balance (cylinder cut) | bitmask: bit0=cyl1 … bit7=cyl8, `1`=OFF. (`00`=all firing, `01`=cyl1 off, `20`=cyl6 off.) Some ECUs (e.g. SR20) use `01`–`08` = cylinder number instead. | `[S1][S3]` |
| `89` | Fuel pump relay | `00`=ON, `01`=OFF per Issue 6. The register table says `00`=OFF, "(`00`=ON for some ECU, SR20 etc)". ⚠ | `[S1][S3]` |
| `8A` | P/Reg control solenoid | `00`=OFF | `[S3]` |
| `8B` | Clear self-learn | `00`=clear (resets register `1C`) | `[S1][S3]` |
| `8C` | IACV-AAC control | `00`=OFF | `[S3]` |
| `8F` | Valve timing solenoid | `00`=OFF | `[S3]` |
| `90` | MAP SW control solenoid | `00`=OFF | `[S3]` |
| `93` | Coolant fan LOW | `00`=OFF | `[S3]` |
| `94` | Coolant fan HIGH | `00`=OFF | `[S3]` |

| 35 | EGT sensor | 91 | Front HO2S heater RH |
| 36 | EGR back-pressure transducer | 94 | TCC solenoid |
| 37 | Knock sensor | 95 | Crank position cog |

| | | 105 | EGR & canister control solenoid |
| | | 108 | Canister purge control valve |
| | | 111–128 | A/T codes (inhibitor sw, speed sensor, shift solenoids, line pressure, fluid temp, …) |

### ⚠ Encoding caveat

- The egroup spec writes the "no fault" reply as `FF 02 55 00` and calls it "55 = no fault". `[S1]`
  That suggests the byte is **`0x55`**, with the code read as the *hex digits*, like BCD.
- openconsult treats the byte as a **decimal** value (`NO_MALFUNCTION = 55` → byte `0x37`). `[S2]`
- These cannot both be right. **Test on the car:** with no stored codes, look at the raw
  byte. If it is `0x55`, display codes as `"%02X"`.
- The 1998 Maxima's OBD-II-era ECU may report **different code numbers** from this
  pre-1996 list. Nissan FSMs for 1996+ cars list codes as P-codes with 4-digit ECM
  numbers. ⚠ Unverified. Compare `D1` output with a generic OBD-II scan of the same fault.

## 10. Other ECUs on the same bus

The third init byte selects the target ECU. `[S3]`

| ECU | Init | Extra commands |
|---|---|---|
| Engine | `FF FF EF` | `D0` info, `D1` DTC, `C1` clear |
| Automatic transmission | `FF FF EA` | `9F` stream all, `D1`, `C1`, `F0` "ECU info" |
| S-HICAS (4WS) | `FF FF E4` | `9F`, `D1`, `C1` |
| Auto A/C | `FF FF DF` | `D1`, `C1` |

The A32 Maxima's A/T ECU may answer on `EA`. Worth trying.

**A/T registers** `[S3]`: `00` VSS-A/T km/h, `01` VSS-meter km/h, `02` TPS V = `v/50`,
`03` fluid temp sensor V = `v/50`, `04` battery V = `v*8/100`, `06` engine RPM = `v*32`,
`08`–`0A` bit registers, `0C` gear = `v+1`, `0D` selector (`83`=P/N, `82`=1, `81`=2, `80`=D, `87`=R),
`0E` speed km/h, `0F` throttle % = `v/2.55`, `10` line-pressure duty % = `v*64/100`, `11` TCC duty %.

A/T bit registers `[S3]`:

| Reg | b7 | b6 | b5 | b4 | b3 | b2 | b1 | b0 |
|---|---|---|---|---|---|---|---|---|
| `08` | Kickdown sw | Closed throttle sw | Power shift sw | W/O throttle sw | ASCD OD cut | ASCD cruise | R-pos sw | OD sw |
| `09` | — | — | — | — | Hold sw | Overrun clutch S/V | Shift S/V B | Shift S/V A |
| `0A` | P/N pos sw | D-pos sw | 2-pos sw | 1-pos sw | — | — | — | — |

## 11. Implementation guide

### 11.1 Suggested architecture

```
transport  (serial port, timeouts, latency, reconnect)
   ↓
protocol   (init, send-with-echo-check, F0, frame reader, stop/drain)
   ↓
ecu model  (register defs + formulas, bit registers, DTC table, per-ECU profiles)
   ↓
apps       (CLI logger → CSV, live gauges/TUI/GUI, DTC read/clear, ROM dump, active tests)
```

Keep the register/DTC definitions in a data file (JSON/YAML/TOML) so other people
can add ECU profiles without touching code.

### 11.2 State machine

```
DISCONNECTED ──open──▶ PORT_OPEN ──send FF FF EF, wait 0x10──▶ IDLE
IDLE ──send cmd+args, verify echo, send F0──▶ STREAMING
STREAMING ──read frames──▶ STREAMING
STREAMING ──send 30, drain until CF (or FE) / timeout──▶ IDLE
any ──timeout/garbage──▶ send 30, drain, re-init
```

### 11.3 Reference Python (pyserial)

```python
import serial, time

INIT = bytes([0xFF, 0xFF, 0xEF])

def open_port(dev="/dev/ttyUSB0"):
    return serial.Serial(dev, 9600, timeout=0.5)   # 8N1, no flow control

def stop(p, timeout=2.0):
    p.write(b"\x30")
    end = time.time() + timeout
    while time.time() < end:
        b = p.read(1)
        if b in (b"\xCF", b"\xFE"):            # spec says CF; Nissboard saw FE
            return True
    return False

def init(p, tries=5):
    for _ in range(tries):
        stop(p, 0.5)                            # in case it was left streaming
        p.reset_input_buffer()
        p.write(INIT)
        end = time.time() + 2.0
        while time.time() < end:
            if p.read(1) == b"\x10":
                return True
    return False

def command(p, payload: bytes):
    """payload e.g. 5A 08 5A 00 5A 01 – echo has cmd bytes inverted, args verbatim."""
    p.write(payload)
    echo = p.read(len(payload))
    expected = bytearray()
    i = 0
    while i < len(payload):
        cmd = payload[i]
        nargs = {0x5A: 1, 0xC9: 2, 0x0A: 2}.get(cmd, 0)
        expected.append(~cmd & 0xFF)
        expected += payload[i+1:i+1+nargs]
        i += 1 + nargs
    if echo != bytes(expected):
        raise IOError(f"bad echo {echo.hex()} expected {expected.hex()}")
    p.write(b"\xF0")

def read_frame(p, expected_len=None):
    while True:                                 # resync on FF + correct length
        if p.read(1) != b"\xFF":
            continue
        n = p.read(1)
        if not n:
            raise TimeoutError
        n = n[0]
        if expected_len is not None and n != expected_len:
            continue
        data = p.read(n)
        if len(data) == n:
            return data

# Example: RPM + coolant + TPS
REGS = [0x00, 0x01, 0x08, 0x0D]
p = open_port()
assert init(p), "no 0x10 from ECU"
command(p, b"".join(bytes([0x5A, r]) for r in REGS))
try:
    while True:
        d = read_frame(p, len(REGS))
        rpm = ((d[0] << 8) | d[1]) * 12.5
        clt = d[2] - 50
        tps = d[3] * 20 / 1000
        print(f"{rpm:6.0f} rpm  {clt:4d} °C  {tps:4.2f} V")
finally:
    stop(p)
```

### 11.4 Gotchas checklist

- Always **stop (`30`) and drain** before sending a new command.
- **Don't parse by scanning for `FF`**. Use the length byte. Data can contain `FF`.
- **Use read timeouts.** Several existing projects hang forever on a silent ECU. `[S2][S4]`
- **Max 20 registers** per `5A` request and **max 8 addresses** per `C9` request. `[S1]`
- Unsupported registers: the behaviour is undocumented. Expect a missing or wrong
  echo. Probe them one at a time.
- Many ECUs need the **engine running or ignition ON** to answer. The ECU must be powered.
- Set the FTDI `latency_timer` to 1 ms for smooth gauges.
- Python 3: write `bytes([0x30])`, not the bare int `0x30` (a Nissboard bug). `[S4]`

## 13. How to verify / reverse-engineer further

1. **Raw terminal test**: with the car at ignition ON:
   ```sh
   stty -F /dev/ttyUSB0 9600 cs8 -cstopb -parenb raw -echo
   printf '\xff\xff\xef' > /dev/ttyUSB0 & timeout 3 xxd /dev/ttyUSB0
   ```
   You should see `10`. (Or use `picocom -b 9600` / `cutecom` in hex mode, which is how
   the egroup did it. `[S1][S4]`)
2. **Register probe**: for each register `00`–`FF`, send `5A <r> F0`. Record whether
   the echo is `A5 <r>` and what values come back. Then stop. This builds a profile of
   what your VQ30DE ECU supports.
3. **Sniff ECUTalk**: this is the best way to learn anything ECUTalk does that isn't
   documented here.
   - Run ECUTalk in a **Windows VM** with the dongle passed through, and capture on the
     Linux host with `usbmon` + Wireshark (`modprobe usbmon`, capture `usbmonN`, and filter
     FTDI bulk transfers. Strip the 2-byte FTDI status header on IN packets).
   - Or try ECUTalk under **Wine**, mapping `COM1` → `/dev/ttyUSB0`
     (`ln -s /dev/ttyUSB0 ~/.wine/dosdevices/com1`), and log with `strace -e read,write`
     or `interceptty`.
   - Or put a second USB-serial adapter's RX on the TX/RX lines on the logic side of the dongle.
4. **ROM dump** with `C9`: `0x8000`–`0xFFFF` in 8-byte chunks (4096 requests). Disassemble
   it (the CPU is typically Hitachi/Renesas H8 or Mitsubishi on these ECUs) to find RAM
   variable addresses and the internal register map. That is the ultimate reference for
   your ECU.
