## 1. Consult handler (serial ISR `consult_isr`, `$4EF5`; reply builder `consult_task`, `$996A`) [ROM]

- **Init:** `FF FF` then only **`ED`** is accepted (`CMPB #$ED` at `$4FAE`). The reply
  is the complement, `12`. Any other ID byte drops back to waiting for `FF`. ECUTalk's
  `EF` never works on this ECU.
- **Accepted command bytes:** `FF` (re-init), `30` (stop), `C9` (memory read, 2 address
  bytes), `5A` (register, 1 byte), `0A` (active test), `D0`, `D1`, `C1`, and **`51`**.
  Anything else gets `FE` back. This matches the car (3.2: unsupported = `A5 FE`).
- **`51` is undocumented:** on `F0` it reports the "seen this ignition cycle" flags
  (`$0810–$0822`) as codes and clears them. It also zeroes test state (`$0E51–$0E57`,
  `$0E78–$0E7A`). Confirmed and pending codes are untouched, but avoid sending it
  until it has been tried on purpose.
- **`5A`:** register numbers `00–61` only (`CMPB #$62`). The RAM address comes from the
  pointer table at `$1000` (2 bytes per register, `$FFFF` = unsupported).
- **Request limit:** a new `5A`/`C9` is refused (`FE`) once the argument buffer
  (`$08D2`, counter `$073B`) holds `$28` = 40 bytes. `5A` stores 1 byte per register and
  `C9` 2 per address, so up to **40 registers** or 20 addresses per request. That is
  more than the usual "20 registers" (checklist 3.3), and untested on the car.
- **`0A <t> <v>`:** `t` in `80–AD` looks up a 2-byte descriptor at `$1160+2(t−80)`
  (§4). A first byte below `08` selects a separate "direct" mode that loads a stream
  list from tables at `$EA3F`/`$EA5B`. It is probably the OBD Mode 6 test results:
  the pointers come in sets that match the FSM's TID list. [inferred]
- **`C9` on `$5D40–$623F` is forwarded to the second processor (§6), so the ROM dump
  has a 1.25 KB hole.** For those addresses the reply builder (`$9AEB`) doesn't read
  this CPU's memory (nor `$FE00–$FFCF` when config bit `$1207.5` is set; it's clear

  through the shared RAM (`$024C/$024E`), and its answer (`$02B6` → `$07E7`) is put into

  frame per request, so **our dump of `$5D40–$623F` is stale reply bytes, not ROM**. It

## `c9_find_hidden` overflows `c9_hidden_addr` / `c9_hidden_idx`

`c9_find_hidden` (`rom/23710-2L904.asm:4256`, called on the `F0` that finalizes a C9 request, `:4160`) walks every queued C9 address and, for each one in a forwarded range (`$5D40–$623F`, or `$FE00–$FFCF` when `$1207.5` is set), appends it to two parallel arrays, bumping `c9_hidden_n` each time — **with no upper-bound check**:

```
5491  LDA $07E1 (c9_hidden_n)
5495  ASL A              ; 2*n
549A  ADC #$07C3         ; &c9_hidden_addr + 2*n
54A0  STB $00,X          ; write entry
...
54AA  ADC #$07D7         ; &c9_hidden_idx + n
54B2  STA $00,X          ; write index
54B4  INC $07E1          ; n++  (never compared to a limit)
```

The loop terminator (`:4319`, `ASL A; CMP $073B; BCC`) bounds it only by `cs_argc`, i.e. the number of queued addresses — not by array capacity.

**Capacities vs. reachable count:**
- `c9_hidden_addr` `$07C3`, `c9_hidden_idx` `$07D7`, `c9_hidden_n` `$07E1` → each array holds exactly **10 entries**.
- A single request can queue **20** C9 addresses (40-byte `cs_argbuf` ÷ 2 — the same `$28` limit section 10 cites), and all 20 can sit in `$5D40–$623F` (a 1280-byte window). So `n` runs to 20, double the capacity.

**What gets clobbered:** for `n ≥ 10`, `c9_hidden_idx[n]` writes at `$07D7+n`, which hits `$07E1 = c9_hidden_n` itself at `n=10` (`:4313` stores the loop position `$0C48` there), then `$07E7 = c9_sub_value` and the `$07E2/$07E4/$07E6` forwarding state above it. `c9_hidden_addr[2n]` runs `$07D7…$07EB` over the same region. The attacker-influenced data is the request index (0–19) and the low byte of `addr−$5000`. Because the write lands on `c9_hidden_n` mid-loop, the count is corrupted while it's still being used as the store index — so the exact footprint is value-dependent, but it is unambiguously writing past both 10-entry arrays into live Consult-handler RAM.

**Why section 10 missed it:** that section reasoned about the *input* side (register index `< $62`, `0A` slot ≤ 45, the `cs_argbuf` → `$08FA` overflow) and concluded "none of these let the caller pick where the write lands." This path is downstream of input validation — the addresses are already-validated 16-bit values — and it's the *count* of in-range addresses, not any single value, that's unchecked. It's reachable purely over the bench Consult link with a normal `C9` request (≥11 addresses in `$5D40–$623F`, then `F0`).
