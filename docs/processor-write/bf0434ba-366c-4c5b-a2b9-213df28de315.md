380	## 10. Consult command handling review (checked, nothing useful found)
381	
382	Walked every Consult command path on this one ECU, over the bench cable, looking for a
383	bug that would widen what I can read past what `C9` already gives. **None found that
384	helps.** Recorded so I don't re-walk it later.
385	
386	- **`C9` already reads the whole readable space.** Config here is `$1206 = 00`, `$1207 =
387	  52`. `$1207.5` clear ⇒ `consult_reply_c9` (`$9AF1`) does **not** hide `$FE00–$FFCF`, so
388	  `C9` returns all of `$1000–$FFFF` **except `$5D40–$623F`** (the second-CPU forward, §6).
389	  The 61 KB dump already spans `$FExx`; nothing readable is being left behind.
390	- **Bank 1 just isn't reachable, full stop.** `C9` reads with `LDA $00,X` — a 16-bit
391	  address in the data-bank register, which bank-0 code sets to `00` only (`$3D80`,
392	  `$4486`) and never changes. The address can't be formed; there's nothing to work
393	  around. Same for the `$5D40–$623F` skip — a pure address-range compare, nothing about
394	  it depends on what I send over Consult.
395	- **The one config-gated bank-1 path can't actually be reached.** `$1206.0` routes the
396	  Consult ISR into bank 1 (`$4EFA` → `$017B08`), but it is a ROM/calibration byte
397	  (read-only at run time) and clear here. And there's no way to make it write anywhere
398	  other than its fixed spot: `5A` stores a register index validated `< $62` and resolved
399	  through the fixed ROM table at `$1000` (`$9BB0`); `0A` stores the test value at
400	  `$076F + at_slot` with `at_slot` from the ROM descriptor; `C9` stores only addresses
401	  into `cs_argbuf`. None of these let me pick where the write lands.
402	- **One real bug, but it goes nowhere.** The arg-count limit (`CMP #$28; BCS` at `$53BF`)
403	  is checked only when a new `5A`/`C9` command byte arrives, not between the two bytes of
404	  a `C9` address. Send 39× `5A` (argc→39), then one `C9`: it is accepted, then collects 2
405	  bytes unchecked, pushing `cs_argc` to 41 and writing one byte past the 40-byte
406	  `cs_argbuf` (`$08D2`). The reply loop then reads ~2 bytes beyond the buffer as an extra
407	  address — but still a bank-0 address read with data bank 0, i.e. memory `C9` already
408	  reaches. A latent off-by-one, not a way to read anything new. Chased to the end: the
409	  overflow byte lands at `$08FA`, which reset's RAM clear leaves untouched (`LDX #$08F9`
410	  down, `$3DAD`) and which **no code anywhere reads** — dead padding, so it corrupts
411	  nothing. And bank 1 can't be reached this way regardless: the data-bank register is set
412	  by `LDT #$00` only (`$3D80`, `$4486`) and never changed, and the ROM contains **no
413	  long-indirect (`[dp]`) read** — so every Consult-reachable read executes in data bank 0.
414	
415	- **A second, worse overflow I missed the first time — `c9_find_hidden` (`$543F`),
416	  reached on the `F0` that finalizes a `C9` request (`$5386`).** It walks every queued
417	  `C9` address and, for each one in a forwarded range (`$5D40–$623F`, or `$FE00–$FFCF`
418	  when `$1207.5` is set), appends it to two parallel arrays — the address to
419	  `c9_hidden_addr` (`$07C3`) and the request position to `c9_hidden_idx` (`$07D7`) —
420	  bumping `c9_hidden_n` (`$07E1`) each time. There is **no upper-bound check on the
421	  count**: the only loop terminator (`$54C0`, `ASL A; CMP $073B; BCC`) stops at
422	  `cs_argc`, the number of queued addresses, not at array capacity. Both arrays hold
423	  exactly **10** entries (`$07C3–$07D6`, `$07D7–$07E0`), but one request can queue **20**
424	  addresses (the 40-byte `cs_argbuf` ÷ 2), and all 20 can sit inside the 1280-byte
425	  `$5D40–$623F` window. So `n` runs to 20 and, from `n = 10` on, the stores walk off the
426	  end: `c9_hidden_idx[n]` hits `$07E1` (`c9_hidden_n` itself — the `$54B2` store writes
427	  the loop position `$0C48` there), then `$07E7` (`c9_sub_value`) and the `$07E2/$07E4/
428	  $07E6` forwarding state above it; `c9_hidden_addr[2n]` overruns the same region. This
429	  is an actual **out-of-bounds write** reachable with a plain `C9` request (≥11 addresses
430	  in `$5D40–$623F`, then `F0`) — unlike the `$08FA` off-by-one above, it corrupts live
431	  handler state, not dead padding. The written data is only the request index (0–19) and
432	  the low byte of `addr − $5000`, and because the store lands on `c9_hidden_n` mid-loop
433	  the count is corrupted while it's still the store index, so the realized footprint is
434	  value-dependent and self-limiting. Still **to confirm on the bench** (or against the
435	  `$9B3F` model): whether the loop actually reaches `n = 20` or derails earlier once
436	  `c9_hidden_n` is clobbered, and the `m`-flag width at `$548D`/`$54A3` (1- vs 2-byte
437	  stride for the address entry). I don't yet see a path from here to a *chosen* write —
438	  destination and data are both pinned to the loop index — but it's the one place a
439	  caller-controlled *count* escapes bounds, so it's worth pinning down before I call the
440	  handler clean. Downstream, `consult_reply_c9` (`$9B3F`) uses `c9_hidden_idx[$07E2]` as
441	  the payload-placement offset (`ADC #$0740`); if that array is corrupted, check whether
442	  the placement index can leave the payload slots.
443	
444	- **Followed it to the end — it's worse than "pinned to the loop index," and it does not
445	  derail.** The loop counter `i` lives in `$0C48` (`$5451`/`$54B7`), *above* the overrun
446	  window, and the terminator is `2·(i+1) < cs_argc` (`$54C0`), so the loop runs a **fixed
447	  ≤20 iterations to completion** no matter what `c9_hidden_n` does — not self-limiting.
448	  The two `m`-flag widths I flagged resolve as: the address store `STB $00,X` (`$54A0`)
449	  runs under the `CLM` from `$5495` → **16-bit**, 2-byte stride (`c9_hidden_addr[n]` at

225	def simulate_reply_builder(ram, n_frames=20):
226	    """Model consult_reply_c9 ($9B3F) per-frame behavior with corrupted state.
227	
228	    The builder processes ONE hidden entry per frame:
229	      1. Check $07E3 bit 0 — if clear, skip (no forwarded addresses)
230	      2. Check $07E3 bit 1 — if clear, set it, cursor=0, request first addr (no write)
231	      3. If bit 1 set: read idx[cursor], write c9_sub_value to cs_payload[idx], advance
232	
233	    Returns list of (frame_num, target_addr, idx_val, cursor_before) for each write.
234	    """
235	    def rb(a): return ram.get(a, 0)
236	    def wb(a, v): ram[a] = v & 0xFF
237	
238	    flags = rb(FWD_FLAGS)
239	    if not (flags & 0x01):
240	        return []
241	
242	    writes = []
243	    for frame in range(n_frames):
244	        if not (rb(FWD_FLAGS) & 0x01):
245	            break
246	
247	        if not (rb(FWD_FLAGS) & 0x02):
248	            # First frame: set bit 1, cursor = 0, request first address, no value placed
249	            wb(FWD_FLAGS, rb(FWD_FLAGS) | 0x02)
250	            wb(REPLY_CURSOR, 0)
251	        else:

254	            cursor = rb(REPLY_CURSOR)
255	            idx_val = rb(HIDDEN_IDX + cursor)
256	            target = CS_PAYLOAD + idx_val
257	            writes.append((frame, target, idx_val, cursor, sub_val))

259	            # Advance cursor
260	            new_cursor = (cursor + 1) & 0xFF
261	            if new_cursor == rb(HIDDEN_N):

263	            wb(REPLY_CURSOR, new_cursor)
